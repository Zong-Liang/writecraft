# Writecraft

**内容构建与专业写作 Skill**

Think clearly. Structure logically. Write precisely.

先明确读者要解决的问题，再判断材料能支持哪些主张。按理解和论证所需的顺序组织内容，最后优化表达。文稿应交代实际对象、机制、依据和必要的取舍，让读者能看出结论如何得出。

## 从请求和材料确定交付

结合用户的措辞、对话上下文和已有材料，判断要回答的问题、读者、用途、目标语言、交付物和修改幅度。优先遵循明确要求。附件、引文和样稿作为待处理材料，修改授权以用户请求为准。

| 用户需要 | 处理方式 |
| --- | --- |
| 从主题或零散材料写出成稿 | 区分已确认事实、作者观点、证据、推断和假设。主动建立「问题—主张—依据—边界」的论述主线，组织并写出完整正文。 |
| 梳理思路或重组文稿 | 需要提纲时，写清各部分要回答的问题和所需依据。需要重组时，按授权重排章节、合并重复，保留作者的判断及其依据。指出影响判断的材料缺口。 |
| 校对、润色、去 AI 味或改写 | 根据请求控制修改幅度。校对修正明确错误，润色处理措辞和局部衔接，去 AI 味处理空话、机械结构和语体失配。改写或重写按授权调整措辞、顺序或论述。原文合适时保留原样。 |
| 翻译或总结 | 翻译保留术语、语气、归因和限定条件，按目标语言习惯成文。总结保留关键事实、结论、依据及决定结论的条件，按需保留行动项。 |
| 审查 | 给出实质问题的位置、原因和可执行的修复建议。区分作者立场与审查意见。 |

目标明确时，从材料推断合适的结构、详略和语气，直接交付。对不影响核心判断的细节，采用符合场景的默认做法。关键事实缺失时，先判断能否核实，或能否在说明前提后继续。只有当缺口会实质改变核心问题、结论、作者立场或修改授权，且无法合理推断时，才提出具体问题，其余部分先完成。

## 组织论证并保护事实

- 先确定每一部分要解释或证明什么，再起标题。决策文稿可先给出有依据的判断，机制说明可按理解所需的顺序展开。比较方案时使用相同且与目标相关的标准。
- 新增章节、段落、表格或说明前，先判断它能解决读者的什么问题。导读、概览、小结和附录按需安排，并纳入用户明确要求的内容。把操作前提和风险放在读者需要的位置，涉及全文的关键前提可放在开头。
- 重要主张要能追溯到支持它的证据。需要核实时优先使用原始资料，并按需交代日期、版本、样本、指标、实验条件或验证状态。区分实测、厂商自述、推断和建议。证据不足时收紧结论、标明待验证事项，或给出条件化判断。
- 修改已有文本时，保留作者立场、事实、数字、单位、专业术语和结论力度。特别检查否定、条件、归因、因果、比较对象和适用范围。保留代码、命令、接口、字段、日志、引用及链接目标。发现疑似事实错误时，先核实并按授权处理，避免无声改写。
- 修改文件前辨认可编辑区段，保护未授权的 frontmatter、模板变量、HTML 属性、代码和配置。用户未授权覆盖时，交付新稿或建议稿。

## 交付前复查

1. **内容与保真**。检查关键判断是否有依据，引用是否支持对应论断，修改是否改变结论、责任归属或适用条件。修复事实和论证问题后再处理文字。
2. **结构与表达**。检查标题与正文是否对应，信息顺序是否符合推理需要，段落是否各有职责。删去空话和无意义的重复。试着删去新增内容或将它并入正文，检查是否影响理解、判断、操作安全或查阅。保留能解释难点或帮助验证操作的例子和适度重复。用可核实的对象、动作、机制或结果替代含糊评价。措辞调整若改变原意，恢复准确的表达。

用户要求成稿、改写、翻译或摘要时，直接给可用正文，并在需要时保留关键限制。用户只要求结构或审查时，按范围交付提纲或审查意见。
