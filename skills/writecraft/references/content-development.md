# 内容构建与结构设计

## 把宽泛主题变成可回答的问题

先确定读者读完后需要做什么。例如，「企业级 E2E 自动化测试调研」可以服务于试点决策。先明确试点要覆盖哪些关键链路，再确定选型标准和扩大试点的条件。现有覆盖率、用例失败率和维护成本只有在材料提供或实际核实后才能作为团队现状写入。

整理复杂材料时，可以内部对照「问题、主张、依据、边界」。从主张回看材料，检查指标或样本是否能支撑措辞。从材料回看问题，去掉无法影响解释或决策的重复信息。作者的立场单独识别，避免把待验证的建议写成作者已经确认的判断。

## 处理决定结论的缺口

| 缺口 | 处理方式 |
| --- | --- |
| 事实可以查证 | 优先查官方文档、正式规范、原始论文或可复核数据。将来源放在所支持的论断附近，按需要注明适用版本、样本或日期。 |
| 观察结果有多种解释 | 说明已知现象和各解释所需的条件。需要时指出哪项新证据能区分它们。 |
| 选型缺少实测 | 在相同评价维度下比较已知差异，区分已核实的能力和待验证的表现。若要给出建议，交代它依赖的约束和可验证的条件。 |
| 关键事实暂时无法确认 | 完成其余部分。涉及该事实的结论写成条件化判断，或保留为待验证问题。 |

例如，方法 X 在数据集 A 的指标 M 上高于基线 B，结论范围就是该数据集、指标和实验设置。要论证其他数据集上的表现，需要相应证据。

## 按阅读目的安排内容

| 阅读目的 | 可用的组织顺序 | 容易漏掉的信息 |
| --- | --- | --- |
| 支持决策或选型 | 需求与约束 → 共同标准 → 候选差异 → 取舍与验证 | 比较条件、实施代价、建议成立的边界 |
| 解释机制或实现 | 要解决的问题 → 关键组成或链路 → 状态变化 → 例子或验证 | 接口、数据状态、失败路径、测试方法 |
| 诊断问题 | 现象 → 证据 → 成因与其他解释 → 处理和验证 | 观察与推断的区分，能够验证修复的结果 |
| 汇报项目 | 目标 → 实际动作 → 完成状态与结果 → 阻塞和下一步 | 已完成、待验证和计划中的事项各自处于什么状态 |
| 呈现研究 | 研究问题 → 方法与材料 → 结果 → 解释与局限 | 样本、指标、实验设置、引用与主张的对应关系 |

按需要选取这些关系，章节数量由实际信息决定。审查结构时，问每段是在提供事实、解释机制、比较方案、限定结论，还是交代行动。合并职责重复的段落，让标题准确指向正文回答的问题。

## 判断新增内容是否必要

在起草或重组结构时，先确定拟新增的内容解决哪个具体缺口。必要的事实、论证、实例、操作方法、适用条件和风险说明都可能有独立价值。设想删去该内容或将它并入正文，检查读者是否仍能顺利理解、判断、操作和查阅。

- **导读和概览**。标题、目录或正文开头已交代内容顺序时，可以直接进入正文。多条操作路径需要按读者目标分流时，可以用简短导读说明各路径的入口。
- **前提和风险**。局部的版本、权限或安全要求放在受影响的步骤附近。对全文都适用的关键前提可以放在开头。
- **例子和小结**。已有步骤能直接操作时，避免逐条复述。例子能讲清概念关系、展示一个边界情况或让读者对照结果验证操作时，可以保留必要的细节。用户指定的学习目标、附录等内容按任务要求组织。
