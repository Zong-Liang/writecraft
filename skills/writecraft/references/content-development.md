# 内容构建与结构设计

## 把宽泛主题变成可回答的问题

先确定读者读完后需要做什么。例如，「企业级 E2E 自动化测试调研」可以服务于试点决策。先明确试点要覆盖哪些关键链路，再确定选型标准和扩大试点的条件。现有覆盖率、用例失败率和维护成本只有在材料提供或实际核实后才能作为团队现状写入。

整理复杂材料时，可以内部对照「问题、主张、依据、边界」，正文结构由读者的问题决定。从主张回看材料，检查指标或样本是否能支撑措辞。从材料回看问题，去掉无法影响解释或决策的重复信息。作者的立场单独识别，避免把待验证的建议写成作者已经确认的判断。

## 处理决定结论的缺口

以下用于构建新内容或按要求调整论证。处理已有文稿时，先遵循入口中的「事实与修改范围」。

| 缺口 | 处理方式 |
| --- | --- |
| 事实可以查证 | 优先查官方文档、正式规范、原始论文或可复核数据。将来源放在所支持的论断附近，按需要注明适用版本、样本或日期。 |
| 观察结果有多种解释 | 说明已知现象和各解释所需的条件。需要时指出哪项新证据能区分它们。 |
| 选型缺少实测 | 在相同评价维度下比较已知差异，区分已核实的能力和待验证的表现。若要给出建议，交代它依赖的约束和可验证的条件。 |
| 关键事实暂时无法确认 | 完成其余部分。涉及该事实的结论写成条件化判断，或保留为待验证问题。 |

例如，方法 X 在数据集 A 的指标 M 上高于基线 B，结论范围就是该数据集、指标和实验设置。要论证其他数据集上的表现，需要相应证据。

## 按阅读目的安排内容

| 阅读目的 | 可用的组织顺序 | 容易漏掉的信息 |
| --- | --- | --- |
| 支持决策或选型 | 需求与约束 → 共同标准 → 候选差异 → 取舍与验证 | 比较条件、实施代价、建议成立的边界 |
| 解释机制或实现 | 要解决的问题 → 关键组成或链路 → 状态变化 → 例子或验证 | 接口、数据状态、失败路径、测试方法 |
| 诊断问题 | 现象 → 证据 → 成因与其他解释 → 处理和验证 | 观察与推断的区分，能够验证修复的结果 |
| 汇报项目 | 目标 → 实际动作 → 完成状态与结果 → 阻塞和下一步 | 已完成、待验证和计划中的事项各自处于什么状态 |
| 呈现研究 | 研究问题 → 方法与材料 → 结果 → 解释与局限 | 样本、指标、实验设置、引用与主张的对应关系 |
| 协调事项 | 相关事项 → 所需回应或动作 | 时间、对象，以及接收者需要确认什么 |
| 表达观点或经历 | 具体观察或经历 → 作者的感受与判断 | 叙述视角、个人语气，以及事实与观点的关系 |

按需要选取这些关系，表中的项目用于检查信息是否够用，无需逐项写成章节。让每段提供事实、解释机制、比较方案、限定结论或交代行动，合并职责重复的段落。导读、附录和其他辅助内容根据阅读、操作或查阅需要安排。前提和限制是否进入正文，按入口中的「说明文字的取舍」判断；影响全文的前提可放在开头，只影响某一步的版本、权限或安全要求放在该步骤附近。

## 前置知识与解释顺序

- **前置知识**。只解释读者尚未掌握且后文会用到的概念，在首次需要时简要说明。多个概念有先后依赖时，先解释读者必须用到的概念，再引入它们之间的关系。读者定位不明的学习文档可从理解机制所必需的基础讲起，再安排深入内容。
- **整体过程**。读者对复杂主题陌生时，先说明要解决的问题和主要环节，再按概念依赖展开。面向熟悉背景的读者，可以直接进入他们要理解、判断或操作的环节。
- **信息密度**。按概念关系分段。一个结论所依赖的定义、证据和条件尽量就近呈现，避免一次引入多个尚未解释且相互依赖的概念。比较多个方案时，先交代共同标准。关键风险和操作条件放在相关动作之前，验证方法紧跟操作，进阶细节按需要后置。
- **理解辅助**。用具体例子解释抽象概念，用流程图说明组件关系，用统一维度的表格呈现差异，用分步说明和可观察的结果支持操作。按具体障碍选用形式。例子和图表承担相同解释任务时，保留更易读的一种。

例如，面向初学者介绍 Canal，可以先说明下游为何需要获知数据变化，再给出「MySQL 记录变更 → Canal 读取日志 → 下游消费变更」的主链路。在解释读取和恢复时，再分别说明 Binlog 和同步位点的作用。给熟悉 Canal 的值班人员写故障说明，则可以从位点恢复的前提、处置步骤和验证方法直接写起。

复查时沿正文顺序读一遍，标出首次遇到却尚无法理解的术语、需要拼接的分散信息和缺失的关系。将解释移到读者需要的位置。复杂机制本身可能需要多次阅读，优先处理可以通过组织信息消除的障碍。

## 标题命名

- **主标题**。根据文体交代主题、对象和必要的范围。正式调研、技术文档和工作材料优先直接命名，省去口号和缺少信息的宣传用语。编辑已有文稿时，改题应符合用户授权，并保留原有选题和文档定位。
- **章节标题**。用简洁名称说清本节讲什么，避免把写作提示或助手对正文的评论当作标题。教程可用读者实际会问的问题，如「如何配置 MySQL Binlog」。用设问、比喻或冒号前，判断它是否让主题更清楚。
- **层级与分类**。同级标题按一致口径划分内容，措辞符合文体。下一级标题应标出更具体的范围，标题长度由表达需要决定。章节职责相近时，先调整内容边界，再修改标题。

| 原题 | 可用标题 | 修改依据 |
| --- | --- | --- |
| 从点击到交付：重塑企业级质量保障 | 企业级 Web E2E 自动化测试技术调研报告 | 交代调研对象、范围和文体。 |
| 关于评审时间优化调整的沟通 | 确认周四评审时间 | 适合协调邮件，让收件人直接识别事项。 |
| 技术选型：两大框架的巅峰对决 | Playwright 与 Cypress 对比 | 直接写出比较对象。 |

复查时先单看各级标题，判断它们是否足以区分各节主题和边界。再对照正文，确认内容覆盖标题所指的范围，且标题的语气和判断力度符合材料。
